# April 2026 Consumer Finance Onsight — design digest (current design basis)

> **What this is.** A self-contained, public-appropriate digest of the **April 2026 Consumer Finance Onsight** (Vancouver, Apr 27–30, 2026, plus a May 1 follow-up), where FCM was **re-designed to build on established DeFi protocols implemented in Solidity on Flow's EVM compatibility layer** — replacing the earlier bespoke full-Cadence "ALP" design. **These are NOT legacy** — they are the basis of the **current** FCM design. Minor evolutions happened after; **details may have evolved, but the big picture still applies** (specific evolution flags at the end).

Candid internal material — team/risk/confidence commentary, revenue/token/fee specifics, milestone dollar figures, and named competitor/vendor assessments — is **omitted**; each source section notes *what* was omitted and points to the access-gated original (see [`external-sources.md`](./external-sources.md), category A; request as *"the transcripts and summaries from the April Consumer Finance Onsight"*).

## The pivot (keystone: *FCM_Onsight_Summary*)
FCM moved from a bespoke in-house Cadence lending protocol (ALP) to **leveraged-yield vaults built atop Morpho Blue** — a battle-tested external EVM lending protocol — leveraging Flow's EVM compatibility. Rationale: **security credibility** (a new bespoke on-chain lending protocol is hard to fund/trust; Morpho carries multiple audits and large AUM), **shared liquidity** (avoid fragmenting Flow's TVL), **speed to market**, and a stronger "bring proven EVM code to Flow" story. Morpho over Aave: isolated markets, no collateral rehypothecation, immutable deployments, velocity-based interest-rate model. Trade-offs accepted: dropping the bespoke stablecoin (MOET) and full lending-parameter customization (Morpho markets are immutable). *Omitted here (see source): revenue/token model specifics, candid internal risk/confidence commentary, competitive-positioning detail.*

## Three-layer architecture
1. **Lending** — Morpho Blue (decided; adopt Morpho's liquidation logic unmodified).
2. **Custodian / vault layer** — the contract holding user funds and constraining actions (the current **ERC4626 outer vault**; was an open decision at the onsight, see workstream 1). Key technical finding: the supply-only Morpho Vault V2 design **cannot act as borrower**, which shaped the vault choice.
3. **On-chain automation** — FCM's only bespoke component and its differentiator (next section).

## Automation: Cadence trigger → Solidity execution (decision doc, provisional, May 1)
Automation decomposes into: **(1) Trigger** → **Cadence** (Flow scheduled transactions are the only on-chain scheduler on Flow); **(2a) Decision logic** → defaults to **Solidity**; **(2b) Execution / token movement** → **Solidity** (assets live on EVM; flash-loan callbacks need synchronous same-frame logic; Cadence→EVM calls are one-way). Pattern: a trivial **Cadence heartbeat makes one call into a Solidity `rebalance()`** (reads health, decides, executes or cleanly reverts), then re-schedules itself. Drivers: Foundry testability (the Flow emulator lacks EVM-RPC), Solidity try/catch enabling self-recovery/rescheduling, co-location with the Morpho/oracle/swap contracts, and small current logic. A future Cadence decision layer is preserved as an additive option. **This is exactly the current "Cadence scheduled transaction pokes a permissionless `rebalance()`" design.** *Omitted here: none material (this doc is largely technical); note it is explicitly Provisional.*

## Curator / "verbs" model + governance roadmap (post-v0.2 doc, early draft)
A **verb** is an atomic vault operation; a **curator** (the Cadence automation, an off-chain keeper, or human governance) composes verbs into flows — so the curator implementation can change without touching the vault contracts. The v0.2 baseline verbs: health check, reach-target-health-factor, swaps, borrow/repay, collateral deposit/withdraw, value-aware asset reads, and withdrawal-liquidity provisioning. The roadmap layers capability across milestones — **vMillions** (circuit breakers, warmup states, per-token risk params, multi-strategy allocation, hardened governance with multi-sig/timelock preparation) and **v1.0** (autonomous + immutable + permissionless + revenue-on: permissionless liquidation, async withdrawals, insurance fund, multi-oracle/DEX routers, governance handoff to multi-sig/DAO). Morpho natively provides health-factor/LTV/liquidation/interest, so those need only vault-side wrapping. *Omitted here (see source): the full capability enumeration and unconfirmed/under-review items; this doc self-flags as an early draft needing product alignment.*

## Workstreams (defined at the onsight)
1. **Custodian / Vault Layer Assessment** — choose the contract that holds funds and constrains actions, against the required "verbs," use-case-specific battle-testing, curator-flexibility-vs-drain-risk, NAV transparency, withdrawal mechanics, SDK, licensing, and stack simplicity. Effectively irreversible for the first user cohort. *Omitted here (see source): named-vendor assessments (license/UX/specifics) and staffing.*
2. **Tracer Bullet (testnet PoC)** — assemble FCM end-to-end from existing components only (no new code) as a learning exercise: a lending market (BTC collateral) + outer vault + DEX swaps + a yield-source vault + a manipulable test oracle, with a **human standing in for automation**, proving deposit → oracle-move → rebalance → unwind/withdraw. (At PoC time, **Aave stood in for Morpho** as no Morpho integration existed yet.) *Omitted here: staffing.*
3. **On-Chain Automation** — the bespoke layer: a Cadence resource owns a COA (an EVM address Cadence controls) acting as the vault **curator**; **automation talks only to the vault**, which orchestrates Morpho (small API surface). Includes the hard "withdrawal-liquidity provisioning" (a multicall within the redeem timelock, guarded against MEV/NAV drawdown). Trigger cadence was undefined at the onsight → since settled to **Flow scheduled transactions**. *Omitted here: none material.*
4. **White-Hat Security Agents** — a continuously-running AI red-team that audits the Solidity code, **supplementing (not replacing) formal audits**. Threat focus: fund drainage via arbitrary call data, NAV manipulation, curator slippage, withdrawal-timing attacks, exploit-pattern replay, and — most pointedly — **untested integration glue code** within otherwise battle-tested protocols. Complements the repo's `security/` harness. *Omitted here (see source): specific candidate tools/vendors, an internal tool name, and resourcing/people.*
